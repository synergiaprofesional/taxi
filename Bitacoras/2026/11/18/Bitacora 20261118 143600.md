# Bitácora Synergia Móvil — Sesión 2026-11-18 143600

## Objetivo
Análisis arquitectónico y estratégico senior para la evolución, escalamiento e independización de **Synergia Móvil**: evaluación de la arquitectura de Telegram Desktop (`tdesktop`), análisis comparativo Tauri v2 vs Electron vs Flutter, diagnóstico crítico del desacoplamiento de Odoo 11 ERP, rechazo de Firebase y selección de **Supabase Self-Hosted** (PostgreSQL + PostGIS + Realtime) sobre servidor propio como nuevo núcleo operativo para la salida a Google Play Store.

---

## ANÁLISIS (gstack + SDD)

### Contexto del Sistema Actual
Synergia Móvil opera actualmente sobre:
- **Cliente:** Flutter 3.x (Dart) compilado a código máquina nativo para Android (Xiaomi Redmi Note 13 Pro / Tablet Lenovo M11) y Windows Desktop (`synergia_movil.exe`, 91 KB).
- **Backend Operativo:** Monolito Odoo 11 Community (Python 2.7/3.5, PostgreSQL relacional) mediante llamadas RPC sincrónicas lentas (`callKw`, `searchRead`).
- **Canal Tiempo Real:** Servidor intermedio Node.js + Socket.IO en puerto `3000`.
- **Hardware:** Impresoras térmicas ESC/POS (TCP 9100, Bluetooth SPP nativo).

---

### Diagnóstico de Causa Raíz (Iron Law de gstack)

#### 1. El Conflicto de Dominios: ERP vs Plataforma de Movilidad
- **Síntoma:** Latencias en garita, bloqueos en base de datos al coincidir facturación contable con despacho de taxis, dependencia de una versión legacy de Odoo (v11, lanzada en 2017).
- **Causa Raíz:** Acoplamiento ilegítimo de dominios de negocio. Un ERP está diseñado para registros contables lentos y transacciones administrativas humanas (partida doble, facturación DIAN, nómina). Una plataforma de despacho de taxis exige respuestas sub-50ms, concurrencia masiva de conductores y tiempo real continuo. Intentar que Odoo gestione el ciclo de vida de los taxis es forzar un camión de mudanzas a competir en la Fórmula 1.
- **Trampa Evitada:** Descartada la idea de "migrar a Odoo 18 o 19". Actualizar el ERP costaría meses y miles de dólares para seguir sufriendo el mismo cuello de botella arquitectónico: un ERP en el camino crítico del despacho.

#### 2. Evaluación de Telegram Desktop (`tdesktop`): Lecciones de Ingeniería
- **Stack:** C++17/20 + Qt (primitivas de ventana/eventos) + motor gráfico custom (`lib_ui`), protocolo binario MTProto multiplexado y base de datos local SQLite embebida + bloques cifrados `tdata`.
- **Lección:** Las aplicaciones de alto rendimiento separan radicalmente el hilo de UI de las operaciones de red e I/O, apoyándose en bases de datos locales indexadas y canales de sincronización por eventos (deltas).

#### 3. Evaluación Crítica: Tauri v2 vs Electron vs Flutter
- **Tauri v2:** Destaca por binarios pequeños (~3 MB) y bajo consumo de RAM (40-60 MB) gracias a Rust. Sin embargo, en Android su UI renderiza sobre el **WebView del sistema**, lo que genera inconsistencias táctiles en pantallas móviles y añade una complejidad excesiva al requerir puentes JNI manuales en Rust para gobernar hardware como impresoras Bluetooth SPP.
- **Flutter (Veredicto):** Se ratifica como el stack óptimo. No usa WebViews; renderiza directamente sobre GPU con motor C++ (Skia/Impeller) a 60-120 FPS. Permite desplegar el mismo código en Windows Garita y Android Play Store con comunicación nativa de hardware vía Kotlin (`MethodChannel`).

#### 4. Rechazo Técnico de Firebase
- **Incompatibilidad de Modelo:** La operación de taxis es 100% relacional (Vehículo $\leftrightarrow$ Conductor $\leftrightarrow$ Tarjeta de Control $\leftrightarrow$ Turno $\leftrightarrow$ Caja). Firestore (NoSQL) carece de claves foráneas obligatorias y `JOIN`s atómicos.
- **Riesgo Financiero:** El cobro por lecturas/escrituras en tiempo real para cientos de taxis genera costos exponenciales e impredecibles.
- **Carencia de PostGIS:** Firebase no ofrece un motor geoespacial nativo robusto para geocercas poligonales de bahías ni distancias Euclidianas/geodésicas.

### Decisiones de Diseño y Solución Arquitectónica (SDD)

| Componente | Opción Descartada | Alternativa Aprobada | Justificación Técnica Senior |
|---|---|---|---|
| **Motor de Base de Datos** | Firebase Firestore | **PostgreSQL 15+ con PostGIS** | Integridad referencial estricta, consultas espaciales nativas (`ST_Contains`, `ST_Distance`) y costo fijo \$0 por consulta. |
| **Infraestructura Backend** | Supabase Cloud / Odoo Directo | **Supabase Self-Hosted (Docker en Servidor Propio)** | Soberanía total de datos para FUNDETAXCOL, sin suscripciones en dólares, APIs REST automáticas (PostgREST) y WebSockets nativos de Postgres (CDC/WAL). |
| **Cliente de Usuario** | Reescritura a Tauri / React Native | **Mantener y Potenciar Flutter** | Código AOT nativo, hardware probado en producción (impresión térmica, Bluetooth), target SDK moderno listo para Google Play Store. |
| **Integración con Odoo** | Conexión directa sincrónica | **Puente Asíncrono Desacoplado** | Supabase maneja la movilidad al 100%. Un webhook / cron nocturno envía a Odoo únicamente el resumen de caja y asientos contables para la DIAN. |

## PLAN DE EJECUCIÓN (ROADMAP PARA PRÓXIMA SESIÓN)

### Fase 1: Despliegue de Supabase Self-Hosted en Servidor Propio
1. Clonar repositorio oficial de Docker Compose de Supabase (`supabase/docker`).
2. Configurar `.env` seguro:
   - Secretos JWT (`JWT_SECRET`, `ANON_KEY`, `SERVICE_ROLE_KEY`).
   - Contraseña de PostgreSQL y activación de extensión PostGIS (`create extension if not exists postgis;`).
   - Parámetros SMTP para emails transaccionales.
3. Exponer a través de Nginx/Caddy con SSL Let's Encrypt (`https://api-movilidad.fundetaxcol.co`).
4. Verificar puertos y consumo de RAM (requiere VPS de 4 a 8 GB de RAM).

### Fase 2: Modelado del Esquema de Movilidad en Supabase Studio
1. Crear esquema limpio e indexado:
   - `bahias` (id, nombre, geocerca `geometry(Polygon, 4326)`).
   - `vehiculos` (placa, marca, modelo, activo).
   - `conductores` (cedula, nombre, telefono, tarjeta_control_vigencia).
   - `turnos` (id, bahia_id, vehiculo_id, conductor_id, estado, creado_en).
   - `recaudos` (id, vehiculo_id, valor, conceptos, impreso).
2. Configurar políticas de seguridad **RLS (Row Level Security)** para aislar operarios por bahía y taxistas por su `user_id`.

### Fase 3: Integración en Synergia Móvil (Flutter)
1. Incorporar paquete oficial `supabase_flutter`.
2. Reemplazar llamadas a `OdooService.callKw` por llamadas directas a Supabase:
   - Stream de turnos en tiempo real: `supabase.from('turnos').stream(...)`.
   - Búsqueda instantánea de placas indexadas en PostgreSQL.
3. Mantener el patrón **Outbox / Offline** con SQLite local (`drift`) para garantizar impresión de recibos térmicos aunque se interrumpa el internet.

### Fase 4: Publicación en Google Play Store
1. Generar Android Keystore de producción (`key.jks`).
2. Configurar `android/app/build.gradle` con variables seguras de firma.
3. Ejecutar compilación de bundle de release: `flutter build app-bundle`.
4. Carga en Google Play Console para pistas de pruebas internas.

## NOTAS TÉCNICAS Y APRENDIZAJES
1. **Separación de responsabilidades:** La movilidad es operacional y en tiempo real; el ERP es administrativo y contable. Mezclarlos en el mismo hilo de base de datos fue el error que causó bloqueos históricos en Fundetaxcol.
2. **Soberanía y Costo Cero:** Disponer de servidor propio permite desplegar Supabase Self-Hosted sin incurrir en cuotas mensuales en dólares por lecturas en Firebase ni atarse a Supabase Cloud.
3. **Flutter se mantiene firme:** No existe motivo técnico para migrar a Tauri o React Native. Flutter ya está compilando a código nativo en Windows y Android, dominando la impresión térmica física sin capas web intermedias.
