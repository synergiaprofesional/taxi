# Bitácora Synergia Móvil — Sesión 2026-10-18 215100

## Objetivo
Resolver la falla de acceso y comunicación HTTPS hacia el servicio de impresión térmica local `Odoo Hardware Proxy` en Windows (`C:\proxyServer`), configurar el proxy inverso Caddy Server v2 en la tarea de Windows con soporte SSL sobre localhost y la IP de red `192.168.6.227`, adaptar `PrinterService` en Flutter para sortear el bloqueo de certificados locales en Android/Windows y compilar/desplegar con éxito en la tablet de campo.

---

## ANÁLISIS (gstack + SDD)

### Contexto del Sistema
El ecosistema de impresión térmica de Synergia Móvil opera con una arquitectura distribuida:
- **Terminales Cliente:** Dispositivos Android (Tablets y Smartphones) y PC Windows Desktop ejecutando la app Flutter.
- **Hardware Proxy Local (`C:\proxyServer`):** Microservicio Python (Flask + Win32print) corriendo en el PC de caja donde está conectada físicamente por USB la impresora térmica de 80mm (`TIQUETES`).
- **Proxy Inverso SSL (Caddy v2):** Administrado mediante una Tarea Programada de Windows (`Caddy`) que ejecuta `caddy.bat` (`c:\windows\caddy_windows_amd64.exe run`), encargado de recibir el tráfico HTTP/HTTPS y reenviarlo al puerto interno `4000`.

### Problema (Iron Law)
1. **Falsa Impresión / Síntoma 1:** Al intentar acceder a `https://localhost` o `https://192.168.6.227/`, el navegador y la app reportaban `ERR_SSL_PROTOCOL_ERROR` ("Este sitio no puede proporcionar una conexión segura") o rechazo de conexión en puerto 443.
   - **Causa Raíz Diagnosticada:** En `C:\proxyServer\Caddyfile`, la directiva inicial estaba configurada como `:80 { reverse_proxy 127.0.0.1:4000 }`. Al declarar `:80`, Caddy desactiva automáticamente HTTPS y no abre el puerto 443. Además, para atender peticiones por IP (`192.168.6.227`), se requiere registrar la IP explícitamente con `tls internal` para que Caddy emita un certificado SAN IP válido.
2. **Síntoma 2 (App Flutter / Tablet Android no imprimía):** Al configurar `https://192.168.6.227` en los Ajustes de Impresora de la app móvil:
   - **Causa Raíz A:** En `PrinterService._imprimirPorUrl`, la condición para activar el Hardware Proxy era `parsed.port == 4000 || parsed.path.contains('hw_proxy')`. En HTTPS sobre la IP directa, el puerto es `443` y el path está vacío, por lo que la condición evaluaba `false` y saltaba el envío de tiquetes para hacer un `GET /` que abría el HTML de inicio sin imprimir.
   - **Causa Raíz B:** El cliente HTTP por defecto de Dart/Flutter en Android rechaza terminantemente certificados emitidos por CAs privadas o autofirmadas (`CERTIFICATE_VERIFY_FAILED: self signed certificate in certificate chain`), abortando la conexión HTTPS hacia la IP del PC de caja.

### Trazado de Datos
```
[Tablet Android / Móvil / PC]
         │
         │ (HTTPS POST /hw_proxy/print_raw o print_xml_receipt)
         ▼
[Caddy Server v2 (Puerto 443 TLS)] ➔ Valida SAN IP 192.168.6.227 con 'tls internal'
         │
         │ (Reverse Proxy HTTP plano)
         ▼
[Python Hardware Proxy (127.0.0.1:4000)]
         │
         │ (Win32print RAW API)
         ▼
[Spooler Windows ➔ Impresora Térmica 'TIQUETES' (80mm)]
```

### Decisiones de Diseño (SDD)
| Alternativa Evaluada | Pros | Contras | Decisión |
|---|---|---|---|
| **A. Forzar sólo HTTP plano (Puerto 80 / 4000)** | Simple configuración. | Inseguro; los navegadores y WebViews modernos bloquean peticiones mixtas (Mixed Content) desde orígenes HTTPS. | ❌ Rechazada |
| **B. Certificado Let's Encrypt público** | Reconocido por todos los navegadores sin alertas. | Inviable para IPs privadas de red local (`192.168.x.x`) sin dominio público y DNS challenge. | ❌ Inviable |
| **C. Caddy `tls internal` + Dart `badCertificateCallback` (Elegida)** | Habilita HTTPS real en puerto 443 para `localhost` y `192.168.6.227`; Caddy mantiene certificados SAN; Flutter permite comunicación segura con la LAN sin colapsar por CAs no públicas. | Requiere aceptar certificado en navegador una sola vez si se entra por Chrome. | ✅ **Implementada** |

## EJECUCIÓN

### 1. `C:\proxyServer\Caddyfile`
**Diagnóstico:** Bloque `:80` impedía que Caddy abriera el puerto 443 o emitiera certificados TLS para IPs locales.
**Cambio:**
```caddyfile
https://192.168.6.227, https://localhost, https://127.0.0.1 {
    tls internal
    reverse_proxy 127.0.0.1:4000
}

http://192.168.6.227, http://localhost, http://127.0.0.1 {
    reverse_proxy 127.0.0.1:4000
}
```
**Por qué:** Proporciona soporte dual nativo: HTTPS seguro en puerto 443 para clientes modernos y HTTP en puerto 80 para retrocompatibilidad, enlazando directamente al backend en el puerto 4000. Recargado en caliente mediante `caddy reload --config C:\proxyServer\Caddyfile`.

### 2. [`lib/services/printer_service.dart`](file:///c:/Workspaces/synergia_movil/lib/services/printer_service.dart)
**Diagnóstico:** `_imprimirPorUrl` omitía el proxy si el puerto era 443 y Dart rechazaba certificados autofirmados en Android.
**Cambio:**
- Incorporado `_createHttpClient()` que instancia un `IOClient` con `badCertificateCallback = (cert, host, port) => true`.
- Implementado `_esDireccionLocal(String host)` para detectar automáticamente rangos LAN (`192.168.x.x`, `10.x.x.x`, `localhost`, `127.0.0.1`).
- Enrutamiento directo y prioritario hacia `/hw_proxy/print_raw` con fallback a `/hw_proxy/print_xml_receipt`.

### 3. [`ERRORES.md`](file:///c:/Workspaces/synergia_movil/ERRORES.md)
**Cambio:** Registrado en mármol el **FIX-009: Caddy Server Local y Error SSL (`ERR_SSL_PROTOCOL_ERROR`) en Windows** documentando la causa raíz, la configuración de `tls internal` y la prueba obligatoria de validación.

### 4. Automatización de Scripts
**Cambio:** Generados y conservados en `scripts/` (bajo la Regla Inviolable #1):
- [`scripts/fix_caddy_https.ps1`](file:///c:/Workspaces/synergia_movil/scripts/fix_caddy_https.ps1): Automatización de configuración, validación y recarga de Caddy.
- [`scripts/test_print_https.ps1`](file:///c:/Workspaces/synergia_movil/scripts/test_print_https.ps1): Script de prueba física RAW sobre HTTPS (`{"result": true}`).
